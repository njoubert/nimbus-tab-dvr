Capture feasibility spike: the extension works, the gesture is real, and force-install needs an enrolled Mac

The extension shape in the sketch works end to end. A web page asks, the service worker gets a stream id, an offscreen document records the composited tab at 1920 by 1080 and 15 frames a second in VP9, every timeslice lands in IndexedDB, and the chunks concatenate into a file ffprobe and Chrome both read.

The gesture requirement in the Chrome documentation is real and comes from one line in Chromium: capture is granted to a tab the user has invoked the extension on, or to an extension whose id Chrome was launched with as --allowlisted-extension-id. Nothing else lifts it. With the launch flag, start and stop ran with no click at all, across three cycles, a page reload, a killed offscreen document and an audio capture. The flag has to be on Chrome's command line, so it needs a launcher and cannot come from policy; without it the fleet gets one click per tab. On this Mac, Chrome refused to force-install the packed extension because the computer is not enterprise managed, so an off-store deployment needs MDM enrolment and the Web Store is the other path.

The recommendation is to continue with the extension, and to put two decisions to the client: whether their machines launch Chrome through something that can pass a flag, and whether the extension goes through the Web Store or their MDM.

What was built

Q1: the gesture is a per-tab grant, and the only substitute is a launch flag

On a fresh tab in Playwright's Chromium 153.0.8010.12 the probe and the real request both returned the documented sentence, with or without <all_urls> in the manifest:

Extension has not been invoked for the current page (see activeTab permission). Chrome pages cannot be captured.

The rule is one condition in chrome/browser/extensions/api/tab_capture/tab_capture_api.cc on main:

if (!extension()->permissions_data()->HasAPIPermissionForTab(
    sessions::SessionTabHelper::IdForTab(target_contents).id(),
    mojom::APIPermissionID::kTabCaptureForTab) &&
    (GetAllowlistedExtensionID() != extension_id)) {
  return RespondNow(Error(kGrantError));
}

GetAllowlistedExtensionID() returns the --allowlisted-extension-id switch. There is no kiosk exception and no host-permission check.

The two System Events methods failed in macOS before they reached Chrome: iTerm2, which runs the session, has no Accessibility permission. Granting it and running NIMBUS_ALLOWLIST=0 ./build.sh test is what tests whether a real keystroke or a click counts. That stays unmeasured.

Six seconds each, two second timeslice. The chunk count varies because MediaRecorder treats the timeslice as a minimum; the bytes say the data is all there. About 1.3 to 1.45 MB for six seconds is 1.7 to 1.9 megabits a second against the 3 asked for, the encoder undershooting on a page that is still apart from the canvas and the video.

With a recording live, the page was reloaded. Its start on load came back ALREADY_RECORDING naming the live recording, Done from the reloaded page stopped it, and the probe after the stop was granted under the flag. While the stream was live the probe said "Cannot capture a tab with an active stream.", a different refusal, so the probe belongs between recordings.

ffprobe reports no duration for any of them, because a MediaRecorder stream writes no duration or cues into its header, so the plan's "sane duration" was measured by decoding. Chrome plays all three. After the offscreen document was killed, Done returned OFFSCREEN_GONE and the spool still held the committed chunks; the loss is what sat in the encoder since the last timeslice boundary.

Q3: tab audio records as an Opus track

With the demo's audio box ticked, the start reply reported audio: true and the file carried a second stream. The offscreen document routes the captured track through an AudioContext so the tab keeps playing. Whether the tab actually went silent without that, and whether the replay is audible, needs ears and was not measured.

Q4: user-level policy is read as a recommendation, and off-store force-install needs an enrolled Mac

Chrome 150 packed the build into a 24,473 byte CRX3 with the same id the manifest key gives the unpacked build. Then scripts/spike/policy.sh install wrote the two keys with defaults write, and a fresh-profile Chrome 150.0.7871.101 showed this on chrome://policy:

PolicyValueSourceApplies toLevelStatus
ExtensionInstallForcelist["[BLOCKED]oibiheibjolbkmifdocjhkfalginaofm;http://localhost:8765/updates.xml"]PlatformCurrent userRecommendedError, Warning
 
Error at ExtensionInstallForcelist[0]: Invalid extension ID.
This computer is not detected as enterprise managed so policy can only automatically install extensions hosted on the Chrome Webstore. The Chrome Webstore update URL is "https://clients2.google.com/service/update2/crx".

Two facts are in that row. A user-level defaults write arrives as a Recommended policy rather than a Mandatory one, so it could not force anything even if it were allowed. And an id that is not on the Web Store is blocked unless the machine is enterprise managed, which on macOS means MDM enrolment. The demo page saw no extension, the managed configuration was never read, and a plain-HTTP update URL was never reached.

The branded Chrome also ignores --load-extension: launched with it and the allowlist flag, chrome://extensions listed only Google Docs Offline. So the end-to-end run with the flag is verified on Chromium 153 and unverified on Chrome 150.

Deviations from the plan

  • The bundler question closed on the first build; esbuild was never tried.
  • fmt still does nothing: Vite brings no formatter, and Prettier is outside the budget until asked for.
  • @types/chrome and @types/node joined the budget, types only, so tsc --noEmit can run.
  • The allowlist flag is the test's default; NIMBUS_ALLOWLIST=0 runs the gesture ladder instead.
  • scripts/spike/managed-probe.mjs was added to read a real Chrome's policy page over the DevTools protocol, because the page hides its rows in shadow roots and ignores synthetic input.

Verified and unverified

Verified by running: the full path from page to file on Chromium 153 with the extension unpacked; the refusal text with and without <all_urls>; the flag granting capture with no gesture; reload, kill and audio; packing a CRX3 with Chrome 150; what Chrome 150 does with user-level policy keys.

Read, not run: the Chromium source of the grant check, fetched at main on 2026-09-09.

Not measured: whether a real click or keystroke counts as an invocation from automation; whether a click-granted grant survives a reload; the flag on Chrome 150 itself; the managed configuration reaching chrome.storage.managed; a plain-HTTP update URL; whether the captured tab goes silent; anything longer than six seconds.
